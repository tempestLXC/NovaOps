# 开发规范

本规范适用于 NovaOps 仓库的所有模块与子项目，旨在保证在 JDK 21 及后续版本上的可维护性、一致性与可持续演进。

## 基本原则
- **开源优先**：优先选择 Apache 2.0、MIT、BSD 等宽松开源协议的依赖，避免强制绑定商业闭源软件。
- **安全默认**：严禁提交任何密钥、密码、令牌或真实生产配置；使用占位符或本地密钥管理方案。
- **向前兼容**：公共接口、数据库 schema 变更需提供向后兼容策略或平滑迁移路径。
- **可观测性**：新增或改动的服务需提供必要的日志、指标与追踪埋点，遵循统一格式。

## 分支与提交
- 使用 `main` 作为稳定分支；特性开发在 `feature/<topic>`，缺陷修复在 `fix/<issue>`。
- 提交信息遵循 `<type>: <summary>`，`type` 建议为 `feat`、`fix`、`docs`、`chore`、`refactor`、`test` 等。
- 每个提交应保持变更最小化，并附带相应测试或文档更新。

## 代码与配置
- Java 代码遵循官方代码规范，避免静态工具抑制（`@SuppressWarnings`）滥用；保持空指针、资源关闭等基本健壮性。
- 配置文件须提供示例或模板，生产机密配置使用外部化方式（环境变量、密钥管理服务）。
- 数据库变更通过迁移脚本（如 Flyway/Liquibase）管理，禁止手工修改生产数据库。
- 接口变更需更新 OpenAPI/Swagger 文档或相应 API 描述。

## 依赖与版本
- 新增依赖需说明用途并评估许可证；弃用或升级依赖时记录兼容性注意事项。
- 优先使用 JDK 21 兼容版本，避免引入需要降级 JDK 的组件。

## 代码评审
- 所有合并请求需通过代码评审；关注点包括功能正确性、测试充分性、性能影响、安全风险与文档完整性。
- 评审意见需在合并前落实或明确后续计划。

## 文档要求
- 新增或变更功能需同步更新相关 `README`、架构说明或配置说明。
- 架构设计或重大改动建议在 `doc/` 下新增设计文档，涵盖目标、方案、影响范围与回滚策略。

## 可观测性与运维
- 统一日志格式（建议使用 JSON）并包含 traceId/spanId，敏感信息脱敏。
- 指标命名统一前缀，避免与第三方系统冲突；需提供仪表盘示例或查询语句。
- 健康检查、就绪探针、限流与熔断策略需在代码与配置中显式声明并文档化。
